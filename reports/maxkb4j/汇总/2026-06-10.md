### 3. 优劣与风险分析

#### 优势/亮点
1.  **架构扩展性**：
    - `DocumentParseEngine` 的设计非常出色，通过 `LocalDParseEngine` 和 `MinerUParseEngine` 的组合，实现了“本地兜底+云端增强”的解析策略。
    - `SourceResourceResolver` 策略模式的应用，使得未来增加新的资源类型（如工具、插件）时无需修改核心逻辑。
2.  **SQL 性能意识**：
    - 在 `DocumentMapper.xml` 中，将原本可能导致笛卡尔积或性能缓慢的 `LEFT JOIN` 计数重构为子查询统计（`p_stats`, `dt_stats`），这在处理大数据量文档时能显著减少内存消耗和查询时间。
3.  **代码现代化**：
    - 使用 Java Record (`EdgeNavigator`) 替代传统的 Getter 类，符合现代 Java 开发趋势，代码更简洁。

#### 劣势/风险
1.  **硬编码配置风险**：
    - `MinerUProperties` 中 `apiUrl` 默认指向 `http://localhost:30000`，虽然有 `@ConfigurationProperties`，但在生产环境下如果忘记配置，可能会导致解析请求超时或失败。
2.  **异步异常处理**：
    - `ApplicationChatService` 中的 `chatMessageAsync` 将返回值改为 `void`。虽然增加了异常日志，但调用方（如 Controller）将无法直接感知异步任务的开始状态，需确保前端通过 WebSocket 或 SSE 能正确处理中断情况。
3.  **事务一致性**：
    - `KnowledgeTagsController` 中的 `addTags` 逻辑是在循环中查询数据库（`count == 0`）再进行 `saveBatch`。在高并发场景下，这种“先查后增”的操作可能存在竞态条件导致重复标签，建议在数据库层面增加 `(knowledge_id, key, value)` 的唯一索引。
4.  **技术债务**：
    - 删除了 `DoclingParseService` 但在 POM 中移除了相关依赖，需确认是否有其他模块仍隐式依赖这些库。
    - `DocumentExportController` 中存在硬编码的字符串常量 `SOURCE_FILE_MISSING`，建议统一放入国际化资源文件或常量类。

**建议：** 针对标签管理，建议增加一个清理任务，定期清理 `document_tag` 表中因文档删除而残留的孤立关联数据（虽然代码中已有部分逻辑，但需确保覆盖所有删除路径）。
